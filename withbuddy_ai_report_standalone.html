기존 챗봇과 다른 점

HR 챗봇이 현장에서 신뢰를 잃는 순간은 공통적이다. 각 문제를 기술 선택으로 직접 해결했다.

문제 01
틀린 답을
자신있게 말한다
모르는 질문에도 그럴듯한 답을 생성 → 직원이 잘못된 HR 정보로 의사결정
WithBuddy 선택
문서 근거 없으면 no_result 선언
→ Slack 알림 → 관리자 문서 추가 → 다음 질문엔 답 가능
자동 개선 루프
문제 02
검색 한 번
실패하면 포기한다
단일 검색 방식 → 질문 표현이 조금만 달라도 관련 문서를 못 찾음
WithBuddy 선택
BM25 + 벡터 하이브리드 1차 검색
→ 실패 시 Agent 폴백 재시도
검색 정확도 82.5% → 93.3%
문제 03
생성된 답변을
검증하지 않는다
LLM 출력을 그대로 전달 → 문서와 무관한 내용이 섞여도 감지 불가
WithBuddy 선택
Self-Verifier가 답변 후 문서 근거 재검증
+ Prompt Caching으로 추가 비용 최소화
질문당 ₩3~6원 유지
문제 04
모델 장애 시
서비스 전체가 멈춘다
단일 LLM에만 의존 → 모델 API 장애 = 챗봇 전면 중단, 복구까지 대응 불가
WithBuddy 선택
매 요청마다 Claude Haiku 먼저 시도 → 장애 시 GPT-4.1-mini 자동 전환 → 다음 요청도 Haiku 먼저 재시도
단일 장애점 제거 · 복구도 자동
핵심 설계 원칙
회사 규정이 바뀔 때마다
모델을 재학습시켜야 한다
파인튜닝 방식 → 규정 변경 시마다 GPU 학습 비용 + 며칠의 재학습 대기 → 회사마다 별도 모델 필요 → 운영 불가 수준의 유지보수
WithBuddy 선택 — RAG 기반 설계
문서 업로드 즉시 반영 — 재학습 없음
모델 1개로 N개 회사 지원 — 멀티테넌트
답변 근거 문서 추적 가능 — 설명 가능한 AI
최신 문서 기준으로 항상 정확 — 지식 고착 없음
사용한 만큼만 과금 — GPU 서버 등 고정 인프라 비용 없음, 질문이 없으면 비용도 없음
With Buddy가 다른 이유
일반 AI는 "아마도, 내 생각에는"이라는 추측성 정보를 내뱉는 경우가 있습니다.
With Buddy는 모르면 모른다고 바로 대답하고, 그 질문을 담당자에게 즉시 알립니다.
이 루프가 반복될수록 AI에게 조직의 지식이 쌓입니다.

INSIGHT · 2026-06~ BM25 한국어 구어체 토큰 미스매치 MITIGATED
현상
"급여명세서 어떻게 봐요?" · "월급명세서 확인하고 싶어요" · "페이슬립 어디서 봐요?" — 같은 개념을 다르게 표현한 단어들이 BM25에서 별개의 토큰으로 처리됨. 문서에 "급여명세서"로 저장돼 있으면 "월급명세서"로 검색 시 히트 누락 발생. 동일한 의미라도 표현이 다르면 BM25는 찾지 못하는 구조적 한계.
근본 원인
BM25는 형태소 단위 exact 매칭. kiwipiepy가 비표준 철자(어떡해, 어케)를 표준 표현과 다른 형태소로 분석해 인덱스 미스매치. 벡터 검색은 의미 유사도 기반이라 이 문제가 없지만 BM25는 어형 변화에 취약.
완화 조치 (근본 해결 아님)
RRF 가중치 조정 — BM25가 미스매치 시 벡터 검색 결과가 순위를 보완하도록 벡터 비중 상향. 구어체 변형은 임베딩 모델이 의미 기반으로 처리하므로 대부분의 케이스 커버 가능.
근본 해결 방향 — 인덱싱·검색 전 용어 전처리 정규화 (월급명세서→급여명세서 등 통일). 현 서비스 규모에서는 RRF 완화 + 케이스별 _QUERY_EXPANSIONS 추가로 충분하여 보류 중.
